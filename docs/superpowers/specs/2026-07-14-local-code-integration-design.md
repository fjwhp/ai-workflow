# 本地代码合并节点设计

## 目标

运营验收通过后不立即完成需求，而是进入独立的“代码合并”节点。人工确认后，系统将隔离 AI worktree 中的变更制作成单一需求提交，并 cherry-pick 到项目配置的本地默认分支。全流程不执行 push。

## 工作流

工作流阶段扩展为：

`运营提需 → 产品 PRD → 研发评审 → 技术设计 → 编码自测 → 代码 Review → 自动化测试 → 运营验收 → 代码合并 → 完成`

运营验收通过后进入 `integration / awaiting_merge`。人工合并和合并后测试全部成功后，需求进入 `integration / completed`。该节点不调用 AI，也不允许自动门禁推进。

## 合并资格

后端是合并资格的唯一权威。只读预检必须确认：

1. 当前需求处于 `integration / awaiting_merge`。
2. 需求已关联项目，项目仓库和默认分支仍然存在。
3. 最新编码证据存在，AI worktree 存在，当前 diff 哈希与证据一致且变更非空。
4. 项目主工作树没有已跟踪或未跟踪的本地修改。
5. 项目主工作树当前分支正是项目配置的默认分支。
6. AI worktree 分支与最新编码 Execution 一致。
7. 当前需求没有正在执行的 AI 或合并操作。

任一条件失败时禁止合并，并在界面逐条展示检查结果和修复建议。

## Git 操作

用户点击“合并到本地分支”并二次确认后，服务端按以下顺序执行：

1. 再次执行完整预检，避免页面状态过期。
2. 在 AI worktree 执行 `git add --all`。
3. 创建单一提交，消息为 `<需求编号> <需求标题>`。
4. 读取生成的源提交哈希。
5. 在项目主工作树执行 `git cherry-pick <源提交哈希>`。
6. 按项目配置依次执行白名单测试命令。
7. 保存源提交、目标提交、目标分支、命令输出和完成时间。
8. 所有测试通过后将需求标记为完成。

系统不得执行 `git push`、远端分支创建、强制重置或自动删除 worktree。

## 失败语义

- 源提交创建失败：不操作目标分支，合并记录标记失败，需求保持待合并。
- cherry-pick 冲突：立即执行 `git cherry-pick --abort`；目标分支恢复到操作前状态，需求保持待合并，并记录冲突文件和错误输出。
- cherry-pick 其他失败：若存在进行中的 cherry-pick，执行 abort；需求保持待合并。
- 合并后测试失败：目标提交保留在本地默认分支，不自动回滚；需求进入 `integration / merge_test_failed`，记录失败命令和输出。人工修复后可重新运行测试，但不得再次 cherry-pick 同一提交。
- 服务重启或重复请求：使用持久化合并记录和唯一的需求活动操作约束防止重复提交或重复 cherry-pick。

## 数据模型

新增 `integration_runs`：

- 需求、项目、Execution 和编码证据 ID；
- 状态：`running`、`conflict`、`failed`、`test_failed`、`completed`；
- 源分支、worktree、目标分支；
- 源提交和目标提交哈希；
- 预检结果、命令结果和错误；
- 创建与完成时间。

数据库中同一需求最多存在一个 `running` 合并记录。完成记录不可覆盖。

## API

- `GET /api/requirements/:id/integration-check`：执行只读预检并返回检查项、源/目标信息和 `allowed`。
- `POST /api/requirements/:id/integrate`：重新预检并执行提交、cherry-pick 和测试；同步返回已创建的合并记录，长操作由状态轮询展示。
- `POST /api/requirements/:id/integration-test`：只允许 `merge_test_failed` 状态重新执行配置测试，不再次 cherry-pick。

需求详情返回最新合并记录，供历史展示。

## 界面

时间线新增“代码合并”。进入该节点后，主区域显示：

- 源 worktree、AI 分支和变更统计；
- 目标仓库、目标分支；
- 编码证据 Git diff；
- Review、测试和验收结论摘要；
- 合并预检清单；
- 最新合并操作、提交哈希、测试命令和错误输出。

右侧操作区提供“重新检查”和“合并到本地分支”。合并按钮只有在预检全部通过时启用，点击后弹窗再次显示目标分支并明确提示“只合并本地，不会 push”。测试失败状态提供“重新运行合并后测试”。

## 安全与审计

- Git 和测试命令使用参数数组执行，不经过 shell 拼接。
- 测试命令只能来自已登记项目的白名单配置。
- API 不接受客户端传入任意仓库路径、目标分支或命令。
- 保存 stdout、stderr、退出码和执行顺序；响应和界面沿用敏感信息脱敏规则。
- 合并操作仅作用于用户已登记的本地项目。

## 测试

- 领域模型：验收通过进入代码合并节点，代码合并完成后才完成需求。
- Git 集成：临时仓库覆盖成功 cherry-pick、脏目标工作树、错误目标分支、证据过期和冲突 abort。
- Store：合并记录持久化、唯一活动记录、完成和测试失败状态。
- API：预检、成功合并、重复请求、冲突和重新测试权限。
- Web：节点、预检清单、确认弹窗、运行状态、提交哈希与失败详情。
- 浏览器验收不对点餐项目执行真实合并；真实合并必须由用户在界面明确点击。

## 非目标

- 不 push 代码，不创建远端 PR。
- 不自动解决冲突。
- 不自动回滚已成功 cherry-pick 但测试失败的提交。
- 不自动删除 AI worktree 或分支。
