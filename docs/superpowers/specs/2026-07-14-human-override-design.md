# Code Review 与自动化测试人工例外通过设计

## 目标

在 Code Review 和自动化测试阶段始终提供人工通过能力。当 AI 结论不能自动推进，但人工已检查成果并愿意承担风险时，可以留下明确意见后继续流程。

## 适用范围

- `code_review`：人工例外通过后进入 `testing`。
- `testing`：人工例外通过后进入 `acceptance`。
- 其他阶段沿用现有审批和门禁规则，不提供本功能。
- 不以打回次数作为入口条件；两个适用阶段始终展示入口。

## 资格规则

后端是资格判断的唯一权威。人工例外通过必须同时满足：

1. 需求当前阶段为 `code_review` 或 `testing`。
2. 当前状态不是 `ai_running`。
3. 当前阶段已经存在至少一个 AI 成果。
4. 审核意见去除首尾空白后不为空。

不满足条件时接口返回 `409` 或 `400`，且不改变需求状态。前端根据服务端返回的资格信息禁用入口并说明原因。

## 数据与审计

复用 `approvals` 审批记录，增加能够区分普通人工审批和人工例外放行的决策类型 `human_override`。记录包含：

- 需求和当前阶段；
- 审核意见；
- 操作时间；
- 当前阶段最新 Artifact ID；
- 当前阶段历史打回次数；
- 当时仍存在的风险和待确认问题快照；
- 放行后的目标阶段。

历史审批记录不可覆盖。人工例外通过不修改 AI 的原始结论，也不伪装为 AI 自动通过。

## 接口与流转

新增专用接口 `POST /api/requirements/:id/human-override`，请求体只接受非空 `comment`。服务端在一个同步操作中校验资格、写入审批记录并推进状态：

- `code_review` -> `testing / ai_ready`
- `testing` -> `acceptance / ai_ready`

需求详情返回人工例外通过资格、累计打回次数和最近审批记录，供界面展示。专用接口避免放宽通用审批接口而影响其他阶段。

## 界面

Code Review 和自动化测试的操作面板始终显示“人工审核通过”按钮。AI 正在处理、尚无当前阶段成果等不具备资格的状态下按钮保持可见但禁用，并展示原因。

点击后打开确认弹窗，展示：

- 当前 AI 结论和摘要；
- 未解决风险与待确认问题；
- 当前阶段累计打回次数；
- 通过后进入的下一阶段；
- 必填的人工审核意见。

提交成功后刷新需求详情。执行过程和审批历史将该记录标为“人工例外通过”，与 AI 自动门禁决定使用不同标签。

## 错误处理

- 重复点击或页面状态过期时，以服务端当前状态为准，拒绝第二次流转。
- 审核意见为空返回 `400 VALIDATION_ERROR`。
- 阶段、状态或 Artifact 不符合资格返回 `409 HUMAN_OVERRIDE_NOT_ALLOWED`，并提供可展示的中文原因。
- 写入审批和推进状态应在同一数据库事务中完成，避免只有审批记录或只有状态变化。

## 测试

- Store：统计指定阶段打回次数，并原子写入例外审批和下一阶段状态。
- API：两个允许阶段成功流转；其他阶段、运行中、无 Artifact、空意见和重复请求均被拒绝。
- Web 逻辑：两个阶段始终展示入口；资格不足时禁用并显示原因；弹窗正确展示风险、次数和下一阶段。
- 回归：现有 AI 自动门禁、普通批准、打回和返工上下文保持不变。

## 非目标

- 不自动提交、合并或推送代码。
- 不把人工例外通过解释为测试通过或代码无风险。
- 不为其他工作流阶段增加同类入口。
