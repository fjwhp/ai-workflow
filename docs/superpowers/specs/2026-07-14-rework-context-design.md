# 打回原因与返工清单闭环设计

## 目标

让用户在返工阶段直接看到为什么被打回、需要修复什么、证据和建议是什么；同时保证界面展示的返工清单与编码 AI 收到的内容完全一致，并在下一次 Review 中逐项核对。

## 界面

需求处于 `returned` 时，在当前返工阶段成果区域顶部显示“打回原因”面板：

- 来源阶段、目标阶段、打回时间和决定者。
- AI 自动门禁或人工审批标识。
- findings、risks 和 openQuestions 汇总。
- S0、S1 默认展开；S2、S3默认折叠。
- 每条 finding 显示标题、严重等级、证据、影响、建议和原目标阶段。
- 每条标记“本轮返工需处理”。

面板不静默截断条目，内容过长时内部滚动。历史打回可从阶段记录查看，当前页面只突出最新未闭环返工上下文。

## 数据模型

新增不可变 `rework_contexts`：

- ID、需求 ID、审批 ID、来源 Artifact ID。
- 来源阶段、目标阶段、决定者类型和审批时间。
- 返工项 JSON、风险 JSON、待确认问题 JSON。
- 创建时间。

同一审批 ID 只能生成一份返工上下文。来源 Artifact 不存在时，将审批意见转换为一条返工项，并标记 `unstructured=true`。

返工项保留原 finding 字段，并增加稳定 item ID 和初始状态 `open`。

## 生成时机

自动门禁打回和人工打回都在审批与状态变更的同一流程中生成返工上下文。自动打回使用本次 Artifact；人工打回优先使用当前阶段最新 Artifact。

历史记录不会追溯重写。对现有 returned 需求，读取时允许从最新打回审批和来源 Artifact 构造只读兼容视图，首次后续写操作再持久化。

## 编码 AI 输入

返工启动时锁定最新返工上下文并写入 Stage Run 输入：

- `reworkRequired=true`
- `reworkContextId`
- 来源阶段和审批信息
- 完整返工项、风险和待确认问题
- 最新编码证据

Codex 最终结果必须返回逐项处理结果：

- `fixed`：已修复，并引用文件、diff 或测试证据。
- `not_applicable`：不适用，并给出可核验理由。
- `blocked`：无法修复，并说明阻塞条件。

编码 Artifact 保存 `reworkContextId` 和 `reworkResponses`。缺少逐项回复时强制人工审核。

## Review 闭环

下一次代码 Review 输入包含原返工清单、本轮逐项回复和新编码证据。Review 对每项输出：

- `closed`：新 diff 或测试证据证明已解决。
- `open`：问题仍存在。
- `blocked`：缺少足够证据。

只允许基于新证据关闭问题，不能仅根据 Codex 自述。新发现追加为新项，原 item ID 保持不变。

## 异常处理

- 来源 Artifact 缺失时显示审批意见和“缺少结构化评审结果”。
- 同一审批重复处理不会生成第二份上下文。
- 编码开始后锁定快照，后续审批变化不修改本轮输入。
- 返工项过多时完整保存并使用滚动区域展示。
- 编码结果没有逐项回复时进入人工审核。
- Review 缺少真实编码证据时不得关闭返工项。

## 测试与验收

测试覆盖自动打回、人工打回、无 Artifact、严重等级排序、幂等生成、Stage Run 输入锁定、Codex 输入一致性和 Review 逐项闭环。

浏览器使用 `REQ-0005` 验证当前编码返工页面：应显示代码 Review v3 的 S0/S1/S2/S3 原因、证据、影响和建议。验证不会中断正在运行的编码任务，也不会 push 或修改点餐项目主工作区。

## 非目标

- 不允许人工随意将 AI finding 标记为已完成。
- 不自动修改 Review 原始 Artifact。
- 不根据自然语言相似度合并不同返工项。
- 不在缺少新代码证据时自动关闭问题。
