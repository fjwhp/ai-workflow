# 状态、门禁与打回规则

## 统一状态

| 状态 | 含义 | 允许的下一状态 |
|---|---|---|
| 草稿 | 输入正在准备 | AI处理中、已取消 |
| AI处理中 | AI 正在执行阶段任务 | 待人工审批、已阻塞 |
| 待人工审批 | AI 成果已提交 | 已批准、已打回、已阻塞 |
| 已批准 | 本阶段门禁通过 | 下一阶段 AI处理中 |
| 已打回 | 指定责任阶段需修复 | 对应阶段 AI处理中 |
| 已阻塞 | 缺少决策、依赖或可靠输入 | AI处理中、已取消 |
| 已完成 | 全部专业阶段完成 | 已关闭 |
| 已关闭 | 运营验收并归档 | 无 |
| 已取消 | 明确终止并记录原因 | 无 |

## AI 结论枚举

- `通过`：无阻塞项，证据充分。
- `有条件通过`：只有不影响当前推进的非阻塞项，必须指定责任人和截止时间。
- `打回`：存在阻塞项或结论依据不足。

`有条件通过`仍需人工明确批准；条件逾期后自动转为“已阻塞”。

## 问题严重度

| 等级 | 定义 | 门禁效果 |
|---|---|---|
| S0 | 安全、合规、数据丢失或核心业务灾难风险 | 必须打回并升级负责人 |
| S1 | 核心功能不可用、验收标准失败或无可行回滚 | 必须打回 |
| S2 | 非核心功能错误、明显维护或性能风险 | 默认打回；人工可记录理由后降级 |
| S3 | 优化、风格或不影响交付的建议 | 可有条件通过 |

## 置信度规则

- `0.90-1.00`：依据完整，可提交正常审批。
- `0.80-0.89`：可提交，但必须突出未知项和验证建议。
- `<0.80`：不得建议通过，转“已阻塞”或“打回”。

置信度不是审批依据的替代品，AI 必须同时给出证据。

## 打回路由

| 问题类型 | 目标阶段 |
|---|---|
| 业务目标、范围、规则或验收标准问题 | 产品 AI |
| 可行性、架构、接口、数据、兼容或回滚问题 | 技术设计 |
| 实现、单元测试、静态检查或构建问题 | 编码与自测 |
| Review 范围或证据不足 | Review AI |
| 测试用例、脚本或环境分类问题 | 测试 AI |
| 业务结果与预期不符 | 先由产品负责人判定责任阶段 |

禁止仅写“有问题”或通过口头沟通打回。每次打回必须使用打回记录表。

## 门禁通用检查

1. 输入材料存在且版本已批准。
2. 输出采用规定模板且字段完整。
3. 事实、推断、假设和未知项明确区分。
4. 所有结论引用可复核证据。
5. S0-S2 阻塞问题均已关闭或被正式打回。
6. 追溯矩阵已更新。
7. 人工审批人、时间和意见已记录。
